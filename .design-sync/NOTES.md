# Hive Design System — sync notes

- **No TypeScript / no `.d.ts` anywhere in the package.** `dist/` is built (esbuild, JS only) but ships no type declarations. Every component is pinned via `cfg.componentSrcMap` (so discovery doesn't need `.d.ts` exports) and given a hand-written `cfg.dtsPropsFor` body derived from each component's destructured props in `src/components/**/*.jsx`. If the repo ever adds real `.d.ts` output, these overrides can be dropped in favor of auto-extraction — re-verify the emitted props match first.
- **`cfg.cssEntry` must be set explicitly to `"dist/ds-bundle.css"`.** The converter only auto-extracts CSS from `import "./x.css"` statements still present in the JS entry; `dist/ds-bundle.js` is esbuild's own already-bundled output, which has no CSS imports left in it (esbuild strips them once extracted to the sibling `.css` file at the original build). Without `cssEntry` set, `styles.css` silently omits all component CSS (`_ds_bundle.css` stays the `@ds-css-runtime` placeholder) — this is easy to miss since the bundle still builds and `validate` doesn't flag it as fatal.
- **Brand fonts (Funnel Display, Inter, Inter Tight) are Google Fonts loaded via `<link>` in the host page** (see `README.md` Setup section) — the package's own CSS has no `@font-face` or `@import` for them. Resolved via `cfg.extraFonts: [".design-sync/fonts/google-fonts.css"]`, a snapshot of the real `https://fonts.googleapis.com/css2?family=Funnel+Display:wght@600;700&family=Inter:wght@400;500;600;700&family=Inter+Tight:wght@600;700&display=swap` response (fetched 2026-06-30) — real `@font-face` rules pointing at `fonts.gstatic.com` woff2 URLs, left as remote `https://` references by `extractFonts` (not copied locally). This is fetched data, not authored content — if Google revs these font files the URLs could 404 eventually; re-fetch the same css2 URL and replace `.design-sync/fonts/google-fonts.css` if that happens.
- 38 named exports across 21 source files (several files export multiple components, e.g. `Table.jsx` → `Table`/`Pkg`/`Stack`/`Cond`). All pass `isComponentName`.
- **Bare/inline components need a dark `var(--bordo)` stage wrapper when authored standalone.** Most of this DS's primitives (Button, Chip, PinChip, Callout, SectionHeading, Pkg, Stack, Cond, Cor, Cmt, Reveal) have no background of their own by design — they're meant to sit on the page's dark `--bordo`/`--surface` background and use light `--ink`/`--muted`/`--coral` text. The capture/review-sheet canvas is white, so an unwrapped standalone preview of these renders as washed-out, near-invisible text — easy to misdiagnose as broken/unstyled (or, for `Reveal`, as a stuck animation — it wasn't; it revealed fine, just illegibly). Fix used throughout: wrap each preview export's root in `<div style={{ background: "var(--bordo)", padding: "28px" }}>`. Any newly-added bare/inline component should get the same treatment.
- **`PinChip` is single-character only** — fixed 32×32px clipped square (`src/components/PinChip/PinChip.css`). Longer strings clip/overflow. Only ever pass a single letter/initial.
- **`SkillSpinePin` used standalone has no flex-row layout.** `.hds-pin-row` is scoped as `.hds-skill .hds-pin-row` in `SkillCard.css`, so it only gets its horizontal flex layout when nested inside a `SkillCard`. Used on its own (as its preview must, since it's graded independently) it falls back to block/stacked layout — still legible and styled, just not the intended row. Real consumers composing `SkillSpinePin` outside `SkillCard` hit the same thing. Not fixed here (a source-level CSS un-scoping call, not a sync-tooling fix).
- **`Footer` has no background of its own** (only a `border-top`, per `Footer.css`) — correct by design, but means its standalone preview renders on whatever page background surrounds it (white in the review sheet). Not a bug.
- **`Logo`'s `mark="full"` only exists in `tone="color"`** (`assets/logos/full_logo.svg` has no black/white sibling — it's a strict superset of `colored_logo_with_description.svg`, 8 extra paths, confirmed by diffing path `d` attributes; visual difference unverified, no SVG renderer available in this environment). Requesting `mark="full"` with `tone="black"`/`"white"` silently falls back to `SOURCES.color.simple` (see `Logo.jsx`) — not a bug, but worth knowing before assuming every tone/mark pair renders something distinct. The SVGs are inlined via esbuild's `loader: { ".svg": "text" }` (added to `build.mjs` for this), not shipped as static asset files — `assets/logos/` itself is dev-time source, not part of the published `dist/` (per `package.json`'s `files: ["dist"]`).

- **`Logo` preview backgrounds**: `tone="color"` and `tone="black"` use white/light background in previews (brand colors are dark bordo + tan, designed for light surfaces); `tone="white"` uses `var(--bordo)` dark background. If SVG content changes to be white-on-dark for color tone, update `Logo.tsx` preview accordingly.

## Re-sync risks
- The `dtsPropsFor` bodies are hand-derived from source, not type-checked — if a component's destructured props change in `src/`, the synced `.d.ts` silently goes stale until someone updates the config entry.
- The Google Fonts CSS snapshot is point-in-time fetched data, not generated from the repo — see above.
- All 39 `.design-sync/previews/*.tsx` were authored by AI subagents (38 original + `Logo.tsx` added on 2026-06-30) working from JSDoc-free, untyped JSX source (prop shapes inferred from destructuring, not verified against real usage in the marketing site this DS was extracted from). Content is realistic but invented, not ported from real product copy — a human pass over `.review.html` is worth doing before treating these as canonical.
