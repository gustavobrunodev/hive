- (capability) CAP-1 (FR-1): abrir uma Spec de UX existente inicia uma sessão do Design Studio; lista todas as Telas antes de gerar qualquer Preview; Spec sem Tela reconhecível gera mensagem explicativa, nunca tela em branco silenciosa
- (capability) CAP-2 (FR-2): Skill de Design System gera automaticamente, por Tela, uma Árvore de Componentes inicial mapeada ao DS ativo, usando exclusivamente Componentes do catálogo; estado de carregamento visível cobre a espera assíncrona
- (capability) CAP-3 (FR-3): alternar viewport do Preview entre presets (mobile/tablet/desktop) e customizado, sem perder estado de edição da Tela; preset ativo sempre visível
- (capability) CAP-4 (FR-4): navegar entre Telas via seletor dedicado; cada Tela mantém Árvore de Componentes e histórico de chat independentes; seletor indica editada vs. auto-gerada
- (capability) CAP-5 (FR-5): selecionar qualquer Componente renderizado no Preview, incluindo aninhados, com destaque visual; nova seleção substitui a anterior, sem multi-seleção na v1
- (capability) CAP-6 (FR-6): editar via Inspetor de Propriedades as props do Componente selecionado, refletindo no Preview imediatamente; prop editável sempre corresponde a prop real do DS; mudança inválida é rejeitada com feedback, nunca aplicada silenciosamente
- (capability) CAP-7 (FR-7): adicionar, remover ou mover Componentes na Árvore de Componentes da Tela ativa; adicionar exige escolher entre Componentes do Adaptador ativo; remover/mover atualiza Preview e Árvore de forma consistente e reversível
- (capability) CAP-8 (FR-8): toda edição via Inspetor ou Árvore reflete no Preview sem ação explícita de salvar; tempo percebido como instantâneo, sem reload completo da Tela
- (capability) CAP-9 (FR-9): desfazer/refazer edições feitas via Inspetor, Árvore ou Chat dentro da sessão da Tela; desfazer uma mudança do Chat reverte exatamente aquela mudança, sem afetar edições manuais posteriores
- (capability) CAP-10 (FR-10): descrever em linguagem natural uma mudança desejada na Tela/Componente ativo via Chat de Iteração Visual; pedido é interpretado no contexto do Componente selecionado quando houver um; histórico do chat persiste na sessão da Tela
- (capability) CAP-11 (FR-11): mudanças da Skill de Design System via chat são aplicadas à Árvore de Componentes e refletidas no Preview, sujeitas a desfazer; usam exclusivamente Componentes do Adaptador ativo; pedido fora das capacidades do DS gera explicação da limitação, nunca mudança parcial/incorreta
- (capability) CAP-12 (FR-12): sistema resolve, a partir de configuração central, qual pacote de DS o Design Studio usa; trocar o DS configurado não exige mudanças no Visualizador/Inspetor/Árvore, só na configuração do Adaptador (e na Skill quando necessário); Specs/Telas existentes não migram automaticamente
- (capability) CAP-13 (FR-13): sistema expõe, para a Skill e para a Árvore de Componentes, o catálogo de Componentes disponíveis do DS ativo e suas props aceitas; catálogo é fonte única de verdade usada tanto pela geração automática quanto pela edição manual, nunca divergem
- (capability) CAP-14 (FR-14): gerar um Bundle de Exportação a partir de qualquer Tela, em qualquer estado de edição; Bundle é autocontido (HTML+CSS+assets inline/empacotados), sem dependência de rede; gerar o Bundle não altera o estado de edição da Tela nem da sessão
- (capability) CAP-15 (FR-15): selecionar mais de uma Tela e gerar os respectivos Bundles em uma única ação; cada Tela gera seu próprio Bundle independente; falha ao exportar uma Tela não impede a exportação das demais
- (constraint) Toda mutação de uma Tela passa por um Command de vocabulário fechado (AddComponent/RemoveComponent/MoveComponent/SetProp) aplicado por um único reducer puro sobre o ScreenDocument; nunca mutação direta da árvore por UI, Skill ou Export (AD-2)
- (constraint) Validação de cada Command acontece antes do dispatch via DesignSystemAdapter.validate(), chamada tanto pela edição manual (Inspetor/Árvore) quanto pela Skill de chat — nunca dentro do reducer (AD-2)
- (constraint) A Skill de Design System só emite Command[]; o lote de um turno de chat é validado e aplicado tudo-ou-nada — se qualquer Command falhar, nenhum é dispatchado (AD-3)
- (constraint) Nenhuma camada (Preview, Inspetor, Árvore, prompt da Skill, Export) importa um pacote de DS diretamente — toda leitura de componentes/props passa por DesignSystemAdapter.catalog() (AD-4)
- (constraint) Construção de DOM no Preview usa exclusivamente APIs seguras (createElement + atribuição de propriedade/atributo) — nunca innerHTML ou markup interpolado; props URL-shaped (href/src) passam por allowlist de esquemas antes de aplicar (AD-4)
- (constraint) Preview roda em iframe sandbox="allow-scripts" (sem allow-same-origin) servido por um protocolo privilegiado same-origin (hive-studio://) com CSP própria por resposta incluindo connect-src 'none'; carregamento inicial nunca via srcDoc, atualizações via postMessage same-origin (AD-5)
- (constraint) Export usa exclusivamente DesignSystemAdapter.renderToStaticHtml() — nenhum segundo gerador de markup paralelo ao Preview (AD-6)
- (constraint) Sessão (documento + histórico de comandos + transcript do chat) persiste em um JSON por sessão no userData, chaveado por (specPathHash, workspaceHash); a Spec de UX é somente leitura para o Design Studio; o token de URL hive-studio:// da sessão é aleatório e não-adivinhável, nunca derivado dessa chave (AD-7)
- (constraint) Desfazer/refazer é um único log linear de Command por Tela, reproduzido desde a origem (replay), sem snapshots persistidos; todos os Commands de um turno de chat desfazem como um único passo agrupado (AD-8)
- (constraint) Skill de Design System fala apenas com o contrato comum AgentSession/AgentEvent (AgentAdapter) — nenhum branching por agentId (Claude vs. Devin vs. GitHub Copilot CLI) (AD-9)
- (constraint) Falhas têm exatamente duas formas: CapabilityViolation (mismatch de catálogo do DS — Inspetor e Chat renderizam igual) e OperationError (tudo mais: agente indisponível, falha de asset do Preview, I/O de export) — nunca uma terceira forma ad hoc (AD-10, AD-11)
- (constraint) Export isola falhas por Tela: uma Tela com OperationError não impede a exportação das demais Telas selecionadas (AD-11, FR-15)
- (constraint) Design System ativo da v1 é @awesome.me/webawesome ^3.11.0 (MIT); NUNCA instalar @shoelace-style/shoelace (arquivado, sucedido pelo Web Awesome) — ver stack.md para o detalhe de licenciamento Pro-tier
- (constraint) Design Studio é registrado como EditorTabKind 'design-studio' no painel viewer existente (mesmo padrão de diff/commit/conflict/review) — não é uma SidebarView nem um dialog modal; uma Tela por vez dentro da aba (AD-1)
- (constraint) Viewport preset (CAP-3) e seleção de Componente (CAP-5) são estado transiente de UI, fora do ScreenDocument — não participam de undo/redo (AD-8) nem de persistência (AD-7)
- (non-goal) Não substitui o Figma nem produz o artefato de marca final — valida estrutura/fluxo/composição, não fidelidade pixel-perfect (PRD §5)
- (non-goal) Não é um construtor de UI genérico: renderiza e edita exclusivamente Componentes do Adaptador de DS ativo, sem HTML/CSS livre nem componentes de outros frameworks (PRD §5, §6.2)
- (non-goal) Sem colaboração multi-usuário / edição simultânea da mesma Tela na v1 — uma sessão é editada por um usuário local por vez (PRD §5, §6.2)
- (non-goal) Não aciona o Figma Agent nem cria telas no Figma diretamente — produz apenas o Bundle de Exportação; a integração com o Figma Agent acontece fora do Hive Desktop (PRD §5, §6.2)
- (non-goal) Sem migração automática de Telas/Sessões entre Design Systems diferentes ao trocar o Adaptador (PRD §5, §6.2)
- (non-goal) Sem histórico de versões persistente entre sessões — cada sessão mantém apenas desfazer/refazer local via replay do command log (PRD §6.2; ver Open Questions sobre reaproveitar o padrão do Second Brain/M12)
- (non-goal) Não atende times que já trabalham direto no Figma sem passar por uma Spec de UX do bmad-ux (PRD §2.2)
- (non-goal) Não modifica o fluxo bmad-ux existente nem seu formato de saída (PRD §2.2, §6.2, §9)
